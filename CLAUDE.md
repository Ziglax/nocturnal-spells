# CLAUDE.md

Guidance for AI agents and developers working on this repo. Every technical claim below is grounded in the current code; when code and this file disagree, trust the code and fix this file.

## What this is

A Planes of Power spell turn-in tracker for EverQuest guilds on Project Quarm: a quartermaster logs parchment turn-ins and the app computes what to secure next and which class is owed the next turn-in.
Vanilla JS single-page front end (index.html + app.js + styles.css) with an optional PHP 8 API (api/) for Discord sign-in and shared state on plain Apache hosting. No framework, no build step, no database, no npm.
Everything guild-specific lives in config.json, api/secrets.php and the tracking state, so another guild can adopt the app without touching code (see Common tasks).

## Domain model and distribution rules

Project Quarm launched PoP in September 2026. Tracked currencies (ITEMS in app.js):

- Spectral Parchment: turns into a random level 63-64 spell.
- Glyphed Rune Word: turns into a random level 65 spell.
- Ethereal Parchment (61-62) exists in the data but is out of scope for v1. Adding a currency means updating ITEMS plus ITEM_SHORT/ITEM_CSS; normalizeState drops log entries whose item is not in ITEMS.

Both items are droppable and stackable on Quarm and are handed to one class librarian NPC in the Plane of Knowledge (all 12 librarians stand inside Myrist the Great Library). Each of the 12 classes has a fixed pool per item, 36 pools total, odds 1 / pool size. pqdi.cc is the source of truth for pool contents and odds; all 36 pools were verified against its quest scripts.

Guild rule for multiclass scrolls: a scroll belongs to the class of the NPC it came from, at that class's level. Example: Destroy Undead is CLR 64 at Vicar Ceraen but NEC 65 at Heretic Drahur. Pools in data/spells.js are flattened accordingly, so a level 65 spell can sit in a Spectral pool; level 65 does not imply the Glyphed pool.

One scroll = one player. The engine NEVER shares or auto-counts across classes. Cross-class provenance (the same physical scroll, matched by scroll itemName, logged at another class's NPC) is display only: obtained* badges, +N counts, tooltips, and a dropped-elsewhere queue alert. If an officer allocates such a copy, they lower that spell's wanted count by hand.

Phase 1 (priorities): each class holds a spell list where every entry has a wanted-copy count (want >= 1) and a priority tier (prio >= 1; several spells of one class may share a tier, tier gaps are allowed). Rounds walk three axes: TIER is the outer axis, copy number the middle, the user-defined class order (state.classOrder) the inner. A tier is fully served, all its copies, before the next tier starts. Phase 1 ends only when every listed spell has all its wanted copies (phase1Complete).

Phase 2 (fair share): each class weighs (M1 + m2Ratio x M2) x pool size, where M1/M2 are mains and second mains (state.weights / state.weights2), m2Ratio defaults to 0.5 (clamped 0..1), and pool size is the class's 63-65 turn-in spell count. share = weight / totalWeight; deficit = share x (totalDone + 1) - done; recommendations are sorted by descending deficit (feed the most-behind class first). ALL logged turn-ins count, including phase 1's, so classes fed heavily in phase 1 start behind.

Duplicates: copies within a spell's want are wanted, not duplicates. Only surplus beyond want (or repeats of unlisted spells) is flagged "roll it" (raid or Discord roll among mains). Duplicates are never blocked.

Recording a turn-in requires stock (inventory[item] > 0), decrements it by one, and pushes a log entry with consumed: true. Undo (log tab) removes the entry by id and refunds stock unless consumed === false (legacy entries without the flag count as consuming). Obtained/duplicate status is derived purely from the log, never stored, so deleting a log entry reverts it everywhere automatically.

## Architecture

| Path | Role |
| --- | --- |
| index.html | Static shell: header (#guild-name, #user-chip, export/import/help), tab nav (data-tab: dashboard, priorities, weights, pools, log), empty main#view that app.js fully owns, help dialog with a condensed version of the user-facing rules |
| app.js | The whole front end in one file, 'use strict', comment-delimited section banners: state (also holds persistence, the server client and boot), data views, engine (phase 1 + phase 2 math), dom utils, NPC map tooltips, rendering, import/export, wiring |
| styles.css | All styles |
| data/spells.js | GENERATED dataset (window.SEED_DATA) from a guild-internal parser, not in the repo. Never edit by hand |
| data/pok_map.js | GENERATED by tools/build_pok_map.py (window.POK_MAP). Never edit by hand |
| config.json | guildName, guildId (Discord server id), sessionEpoch, roles.officer / roles.raider (arrays of role ids) |
| api/*.php | PHP 8 API: login/callback/logout (Discord OAuth), me, state, health, lib (shared helpers), secrets.sample.php |
| api/secrets.php | Discord client id/secret, redirect_uri, app_secret. NEVER committed; api/.htaccess also denies HTTP access to it |
| storage/ | Server-side state.json + state.lock, denied to HTTP by storage/.htaccess |
| tools/build_pok_map.py | Generator for data/pok_map.js from a Brewall map file |

Three backend modes; MODE starts 'local' and CAN_WRITE true, then boot() decides by fetching api/me.php:

- server: me.php returns 200 with perm. USER is set, CAN_WRITE = (perm === 'write'), state comes from GET api/state.php (doc.rev into serverRev, doc.state through normalizeState). Officers write, raiders read.
- login: me.php returns 401. renderLogin() shows a "Members only" card whose sign-in button is a plain link to api/login.php. Tab clicks are inert in this mode.
- local: the fetch throws (static hosting, python -m http.server) or the body has no perm. Full write access, state in localStorage key 'spelltracker.v1' (legacy read fallback 'nocturnal.spells.v1'; writes always go to the new key only).

Server sync: save() branches on MODE. In server mode it debounces pushState() by 600 ms (and is a no-op when !CAN_WRITE); otherwise it writes localStorage in a try/catch. pushState POSTs {rev: serverRev, state} to api/state.php with headers Content-Type: application/json and X-Spelltracker: 1. POST, not PUT, because some shared hosts block PUT. On 409 the client adopts the server version, toasts who saved first, and DISCARDS the local edit. On 401 MODE flips to 'login'. Other errors toast the status plus the server's message; network failure toasts "Server unreachable, last change not saved." commit() = save() + render() is the standard mutation finalizer.

Rendering is a full re-render: render() calls view.replaceChildren() and dispatches on activeTab through a renderers map. DOM is built with the h() helper. The record-flow selection (record = {item, cls}) is transient and never persisted. Read-only raiders are also enforced client-side (render disables every control in #view, mutators early-return, import label hidden, drag arming checks CAN_WRITE), but that is UI courtesy only: the API's require_perm('write') is the real gate.

normalizeState(raw) is the single sanitizer for ALL incoming state: localStorage load, server load at boot, 409 conflict reload, and JSON file import. It backfills classes added to seed data, coerces numbers, drops malformed log entries, rebuilds classOrder to exactly the current CLASSES, and migrates legacy fields. Any new state entry point must go through it.

CLASSES is the alphabetically sorted list of seed-data class names and drives every UI listing; the phase 1 class priority order is deliberately separate and user-defined in state.classOrder.

Branding: loadBranding() fetches config.json at boot and uses guildName for the #guild-name span and document.title ('<guild> Spell Turn-ins'); export filenames are slugged from it ('<slug>-spells-state.json', fallback 'guild'). On fetch failure the app keeps neutral branding. This is the main reuse hook for another guild.

## Persisted state shape

Exact fields (defaultState in app.js):

```js
{
  inventory:  { "Spectral Parchment": number, "Glyphed Rune Word": number },
  weights:    { [className]: number },   // M1 mains per class
  weights2:   { [className]: number },   // M2 second mains per class
  m2Ratio:    number,                    // clamped 0..1, default 0.5
  priorities: { [className]: [ { name: string, want: number >= 1, prio: number >= 1 } ] },
  classOrder: string[],                  // phase 1 class order, user-defined
  log: [ { id: string,                   // crypto.randomUUID()
           ts: number,                   // Date.now()
           item: string,                 // one of ITEMS
           cls: string, spell: string,
           consumed: boolean } ]
}
```

Legacy migrations inside normalizeState: a plain-string priority entry becomes {name, want: max(1, round(Number(phase1Target) || 2)), prio: listPosition + 1} (the default 2 replaces a missing, non-numeric or zero phase1Target before rounding); the top-level fields phase1Target, bankCounts and bankFile are deleted.

## API contract

All JSON endpoints return Content-Type: application/json; charset=utf-8 and Cache-Control: no-store. Sessions are stateless HMAC cookies; there is no database and no server-side session store.

Cookie format: base64url(JSON payload) + '.' + hex HMAC-SHA256 of the body keyed with app_secret; verified with hash_equals; an exp in the past is rejected. All cookies: path=/, HttpOnly, SameSite=Lax, Secure when HTTPS (direct or via X-Forwarded-Proto). The session cookie 'spelltracker_sess' payload is {uid, name, perm ('read'|'write'), epoch, exp = now + 7 days}. Sessions last 7 days; role changes on Discord apply at the next login. current_user() additionally rejects any session whose epoch differs from config.json's sessionEpoch.

Endpoints:

- GET api/login.php: no auth. Sets the OAuth state cookie 'spelltracker_oauth' (signed {state: 32-hex random, exp: now + 600 s}) and 302-redirects to https://discord.com/oauth2/authorize with scopes exactly 'identify guilds.members.read'.
- GET api/callback.php: verifies and deletes the state cookie, requires the state query param to match via hash_equals. Exchanges the code at POST https://discord.com/api/v10/oauth2/token (credentials and redirect_uri from secrets.php), then reads role ids from GET /users/@me/guilds/{guildId}/member. Any role in config roles.officer gives perm 'write'; otherwise any role in roles.raider gives 'read'; otherwise 403. Display name: guild nick, then global_name, then username, then 'unknown'. On success it sets the session cookie and 302-redirects to '../'. Errors are HTML pages, not JSON: 403 (Discord ?error, state mismatch, no qualifying role), 400 (no code), 502 (token exchange or user lookup failed).
- GET api/me.php: 401 unauthenticated; else 200 {user: {id, name}, perm, expiresAt}.
- POST api/logout.php: 405 for any other method; requires the CSRF header; expires the session cookie; returns {ok: true}. POST plus header so a cross-site GET cannot force-log-out a member.
- GET api/state.php: perm 'read' (any authenticated member). Returns the full doc {rev, state, updatedAt, updatedBy}.
- POST or PUT api/state.php: perm 'write' plus CSRF header. Body must be JSON {rev: int, state: object} or 400. Bodies over 2,100,000 bytes get 413; both Content-Length and the actual php://input bytes are checked, because post_max_size does not apply to php://input on PUT. rev mismatch returns 409 with the full current doc. On match it stores {rev: rev + 1, state, updatedAt: gmdate('c'), updatedBy: session name} and returns 200 {rev, updatedAt}. Any other method: 405.
- GET api/health.php: perm 'read'. Returns {php, curl, https, storageDirExists, storageWritable (probed by writing and deleting storage/write-test.tmp), storageGuard, stateExists, you: {name, perm}}.

CSRF: every mutating request must carry the header 'X-Spelltracker: 1' or it gets 400 {"error":"Missing request header."}. Enforced on state.php POST/PUT and logout.php. Keep this header on any new mutating call.

Auth failures from require_perm(): 401 {"error":"Not authenticated."} without a valid session; 403 {"error":"Read-only access."} when write is required but perm is 'read'.

Storage: every state read and write runs under an exclusive flock (LOCK_EX) on a dedicated storage/state.lock that is never renamed; state.json itself is replaced atomically (write to temp, then rename). A failed lock returns 500. If state.json exists but is invalid JSON, the API returns 500 and refuses to touch it rather than silently replacing it. Missing or empty gives the initial doc {rev: 0, state: null, updatedAt: null, updatedBy: null}. with_state_lock creates storage/ (0755) if missing and recreates storage/.htaccess whenever absent.

Config validation: secrets() returns 500 if api/secrets.php is missing, any value is empty or still starts with 'YOUR_', or app_secret is shorter than 32 characters. cfg() returns 500 if config.json is missing/invalid or lacks guildId or roles. Discord API calls use curl with a 10-second timeout against https://discord.com/api/v10.

## Data pipeline

pqdi.cc is the source of truth: pool contents, pool odds ("random 1/N") and the NPC spawn coordinates all come from or are verified against it.

### data/spells.js (window.SEED_DATA)

A generated dataset. The generator is a guild-internal parser (a one-shot consolidation of the guild's bank export, verified against pqdi.cc) that is not part of this repo; the file's header comment still names it. Never edit the file by hand: to change the dataset, replace the whole file with one matching this schema and verify every pool against pqdi.cc. Top-level keys:

```
{
  generatedFrom: string,   // source export filename
  classes: [ { name,       // class name, e.g. "Cleric"
               npc,        // that class's PoK librarian
               spells: [ { name, level: int|null, itemName: string|null,   // itemName = the scroll item, e.g. "Spell: Death Pact"
                           era: 'Kunark'|'Velious'|'Luclin'|'PoP'|null,
                           turnins: [ { item, npc, denom } ] } ] } ],      // item is one of the three parchments; denom = pool size (odds 1/denom)
  pools: { [npcName]: { [itemName]: { denom: int, spells: [ { itemName, name, level } ] } } },
  validation: [ string ]   // 'OK |MISMATCH <npc> [<class>] <item>: <found>/<denom>'; all OK in the current file
}
```

pools is FLATTENED per the guild rule: each pool spell is attributed to the NPC's owner class at THAT class's level; multiclass scrolls are not shared across classes. The app has NO runtime dependency on the bank export.

### data/pok_map.js (window.POK_MAP)

Generated by tools/build_pok_map.py from Brewall's poknowledge map, with NPC spawns from pqdi.cc. Schema:

```
{ bounds: [minA, minB, maxA, maxB],      // map units, current file [-1535, -959, 383, 959]
  stroke: int,                            // current 8
  paths: [ { d, c } ],                    // one chained SVG path string + stroke color
  labels: [ { x, y, t } ],                // two 'Bank' labels + one synthetic 'Library' label
  npcs: { [npcName]: { x, y, hint } } }   // 12 NPCs; hint = human 'which floor' locator
```

Regenerating: `python tools/build_pok_map.py <poknowledge.txt> [labels.txt]`. Stdlib only. The Brewall map file is NOT stored in the repo and must be re-downloaded. The script keeps L-segments, tracks segments with both z > 20 as the library floors, drops segments shorter than MIN_SEG = 12 map units (raising the threshold in steps of 4 until at most MAX_SEGS = 3500 remain), computes bounds and stroke = max(2, extent/240), chains all segments into one path reusing the pen position, keeps only 'Banker' P-records (deduped within 150 units) as 'Bank' labels, synthesizes a 'Library' label under the high-z footprint, and warns if any NPC marker falls outside the bounds.

### Runtime consumption

index.html loads data/spells.js and data/pok_map.js as plain scripts in <head>, BEFORE app.js (which runs with defer). This order is required: app.js dereferences window.SEED_DATA at parse time. POK_MAP is pre-transformed to map space at generation time, so the NPC hover minimap draws paths, labels and markers straight into an SVG (viewBox from bounds plus padding) with zero coordinate math in the app.

## Hard rules and conventions

- Everything in English: code, comments, UI strings, commit messages, docs.
- NEVER use em dashes or en dashes anywhere (code, docs, UI, commits, replies). Plain hyphens only: ranges are written 63-64; otherwise use colons, commas or parentheses.
- Vanilla JS. No framework, no build step, no bundler, no npm, no transpiling. The app must keep working from a plain static file server.
- No runtime coupling to any guild bank export. The export was a one-shot consolidation source for data/spells.js; the app itself only tracks logged turn-ins.
- One scroll = one player. Cross-class copies are display only and the engine never auto-counts them; allocation is the quartermaster's manual call.
- All incoming state, whatever the source, goes through normalizeState().
- Every mutating API request keeps the 'X-Spelltracker: 1' header.
- data/spells.js and data/pok_map.js are generated artifacts, never edit them by hand. For pok_map, change tools/build_pok_map.py and rerun it; for spells.js (guild-internal generator), replace the whole file with one matching the documented schema.

## Gotchas

- Map coordinate convention. Brewall/EQ map files store records 'L a1, b1, z1, a2, b2, z2, r, g, b' where a = -X(game) and b = -Y(game). build_pok_map.py uses those (a, b) values unchanged (no axis transform), so drawing map coords directly in SVG puts north up and east right; orientation was calibrated against the library footprint (the only high-z structure) and the zone-stone labels (Halas north, Neriak south). NPC spawns are entered in the script's NPCS dict as (game Y, game X), the order pqdi.cc prints them (documented at build_pok_map.py:7-8; the repo contains no /loc reference), and converted with map_x = -X_game, map_y = -Y_game. Example: Vicar Ceraen (114, 931) becomes {x: -931, y: -114} in the generated file.
- sessionEpoch force-logout. Incrementing sessionEpoch in config.json invalidates every outstanding session at once (current_user rejects a mismatched epoch) without rotating app_secret. Use it after demoting an officer.
- 409 rev conflicts: see Server sync in Architecture. Do not add merge logic on 409.
- .htaccess deployment. api/.htaccess (denies secrets.php and secrets.sample.php even if PHP handling is disabled on the host, Require all denied with a Deny from all fallback for pre-2.4 Apache) and storage/.htaccess (denies the whole directory) MUST reach the server; FTP clients commonly skip dotfiles. The API recreates the storage guard by itself when absent, but not the api one.
- secrets.php never committed: see the api/secrets.php row in the Architecture table.
- Script load order: see Runtime consumption in Data pipeline.
- localStorage keys: see the local backend mode in Architecture.
- state.php body limit: see API contract.
- Client-side read-only is cosmetic: see the rendering paragraph in Architecture.

## Common tasks

### Adapt the app for a new guild

1. Edit config.json: guildName (brands the header, title and export filenames), guildId (Discord server id), roles.officer and roles.raider (arrays of Discord role ids; officers write, raiders read), sessionEpoch (leave at 1).
2. Create a Discord application, add the OAuth2 redirect https://YOUR-DOMAIN/api/callback.php, copy the client id and secret.
3. Copy api/secrets.sample.php to api/secrets.php and fill discord_client_id, discord_client_secret, redirect_uri (exact match) and a random app_secret of 32+ characters. Never commit it.
4. Deploy per README "Hosting (Discord auth)". Set the class priority order, per-spell tiers/wanted copies and M1/M2 weights in the UI: that is state, not code, and moves between installs via Export state / Import state.
5. If the target server is not Project Quarm, rebuild data/spells.js to the schema in Data pipeline, verifying every pool against pqdi.cc.
